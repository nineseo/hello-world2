# Свой сервер и Claude Code на нём: как это устроить

## 1. Короткий вывод

Решения владельца: **Claude Code работает на сервере, git хранится на сервере, GitHub не используем.** Это рабочая схема. Что важно учесть:

1. **Claude Code не от root.** Root нужен один раз для первичной настройки (скрипт `server/bootstrap-server.sh`). Дальше агент работает под обычным пользователем `vuli`: агент с правами root на сервере может по ошибке сломать всё.
2. **Вход по SSH выбираете вы.** Скрипт спрашивает режим: 1 строгий (без root и паролей), 2 root только по ключу, 3 как есть (root и пароли разрешены). Режим 3 допустим, если пароль очень длинный и случайный, но сервер в интернете подбирают боты постоянно. Запасной вход есть всегда: консоль управления у провайдера (VNC/рескью-режим), поэтому потеря ключа не лишает доступа.
3. **Домен «пользователю» не добавляют.** Он задаётся в DNS на Internet.bs (записи указывают на IP сервера), сайт принимает Caddy внутри Docker.
4. **Код живёт только на сервере.** Поэтому резервные копии вне сервера обязательны, иначе при потере диска пропадёт всё (одна из первых задач).

Что теряем без GitHub: облачные сессии Claude Code на claude.ai/code работают с GitHub, значит, будем работать только в Claude Code на сервере (или на вашем компьютере). Автопроверки GitHub Actions заменяем скриптом `scripts/ci.sh` и git-хуком на сервере.

## 2. Где живёт git
- Рабочий репозиторий: `~/vuli` (клон), «главный» bare-репозиторий: `/srv/git/vuli.git`.
- Позже можно поставить **Forgejo** (веб-интерфейс git на вашем сервере: просмотр кода, задачи, проверки). Для начала хватает обычного git.
- Не-серверная копия: ежедневный `git bundle` или зеркало на второй сервер/хранилище, зашифрованно.

## 3. Как передать Claude Code всё, что мы делали

История чата не переносится, переносятся файлы:
- `docs/` (решения, бриф, курс, конкуренты, домены и знаки), `prototype/`, `server/`, `templates/`;
- `CLAUDE.md` в репозитории `vuli`: Claude Code читает его при запуске (шаблон: `templates/vuli-repo/CLAUDE.md`);
- `docs/10-tasks.md`: задачи по порядку.

Архив со всем этим (`vuli-handoff.zip`) я прикладываю отдельным файлом, чтобы не нужен был GitHub: загрузите его на сервер командой `scp`.

Правило работы: после каждой задачи Claude Code обновляет `docs/02-decisions.md`, отмечает задачу в `docs/10-tasks.md` и делает коммит.

## 4. Пошагово

**Шаг 1. Ключ на вашем компьютере.** `ssh-keygen -t ed25519 -C "vuli"`. Файл `.pub` публичный, второй секретный (никому не отправлять).

**Шаг 2. Сервер.** VPS: Ubuntu 24.04 LTS, 2 ядра, 4 ГБ, 40 ГБ. Если провайдер просит ключ при создании, вставьте публичный.

**Шаг 3. Загрузить архив.** С вашего компьютера: `scp vuli-handoff.zip root@IP-сервера:~/` (если вход root по ключу или паролю работает до настройки).

**Шаг 4. Первичная настройка (один раз, от root).**
1. `ssh root@IP-сервера`
2. `apt-get install -y unzip && unzip -o vuli-handoff.zip -d /root/handoff`
3. Прочитайте `/root/handoff/server/bootstrap-server.sh` и запустите: `bash /root/handoff/server/bootstrap-server.sh`. Выберите режим SSH.
4. Не закрывайте консоль: во втором окне проверьте вход `ssh vuli@IP-сервера`.

**Шаг 5. Файлы проекта у пользователя vuli.**
```
sudo cp -r /root/handoff ~vuli/vuli-docs && sudo chown -R vuli:vuli ~vuli/vuli-docs
sudo -u vuli git init --bare /srv/git/vuli.git
sudo -u vuli git clone /srv/git/vuli.git ~vuli/vuli
sudo -u vuli cp ~vuli/vuli-docs/templates/vuli-repo/CLAUDE.md ~vuli/vuli/CLAUDE.md
```

**Шаг 6. DNS на Internet.bs.** Запись A: `staging` → IP сервера. Позже `@` и `www`.

**Шаг 7. Claude Code.** Под пользователем vuli установите по официальной инструкции (code.claude.com/docs), войдите в аккаунт по ссылке, которую откроете на своём компьютере. Запускайте в `tmux`: `tmux new -s vuli`, затем `cd ~/vuli && claude`.

**Шаг 8. Первое сообщение.**
```
Прочитай CLAUDE.md и файлы в ~/vuli-docs: docs/00-start-here.md, docs/02-decisions.md, docs/07-site-build-brief.md, docs/09-server-and-claude-code-setup.md, docs/10-tasks.md. Выполняй задачи из docs/10-tasks.md по порядку, начиная с T01. После каждой задачи обнови docs/02-decisions.md, отметь её в docs/10-tasks.md и сделай коммит. Git у нас на этом сервере (GitHub не используем). Я не программист: объясняй простыми словами. Перед командами, которые меняют сервер, объясняй, что и зачем. Не проси вставлять пароли в чат.
```

## 5. Правила безопасности (обязательно)

- Claude Code работает **не от root**, в режиме с запросами разрешений. Не включайте режим «пропустить все разрешения» на сервере с данными.
- Перед крупным заданием сделайте снимок диска у провайдера (snapshot).
- Секреты (пароль БД, ключи Resend) лежат в `.env` на сервере с правами `chmod 600` и не попадают в Git. Не вставляйте их в чат.
- Группа docker у пользователя даёт почти права root: поэтому на боевом сервере с реальными данными лучше разделить стенд (где работает Claude Code) и боевой сервер.
- Вход в Claude на сервере хранится на диске: если сервер взломан, отзовите сессию в аккаунте Claude.
- Двухфакторная защита: регистратор, аккаунт хостинга, Claude, почта.
- Ежедневные копии базы данных вне сервера (одна из первых задач).
- Если выбран режим SSH 3 (root и пароли разрешены): пароль root длиной не менее 20 случайных символов, fail2ban включён, обновления включены.

## 6. Что я не проверял
Скрипт `server/bootstrap-server.sh` не запускался на реальном сервере (проверен только синтаксис). Команды установки Claude Code и ограничения облачных сессий сверяйте с официальной документацией: они меняются.

## 7. Один сервер на старте (решение владельца)

Пока сайт закрытый (стенд для администраторов, без реальных пользователей и платежей), можно держать всё на одном сервере: Claude Code, git и стенд. Правила, чтобы это было безопасно:
- На сервере только стенд `staging.vulilang.com`. Реальных данных пользователей и платежей пока нет.
- Перед крупным заданием: снимок диска у провайдера.
- Ежедневные копии вне сервера (задача T04) включаем сразу.
- Claude Code работает под пользователем `vuli` и с запросами разрешений.
- **Триггер для разделения:** до того как открыть сайт для настоящих пользователей или принимать оплату, боевую часть выносим на отдельный сервер (или хотя бы в отдельного пользователя с отдельными копиями). Тогда агент не будет сидеть рядом с реальными данными.
