# Бриф на создание сайта (фаза 1: закрытый стенд)

Для: новой сессии Claude и разработчиков. Владелец проекта не программист: объясняй простыми словами, не проси вставлять секреты (пароли, ключи) в чат.

## 0. Контекст

- Продукт: Vuli, приложение-самоучитель языков (первый язык: турецкий, интерфейс на русском). Персонаж: собака (оригинальный образ, выбор не завершён).
- Домен куплен: **vulilang.com** (регистратор Internet.bs). Один основной домен; всё остальное на поддоменах.
- Прочитай: `docs/00-start-here.md`, `docs/02-decisions.md`, `docs/03-course-skeleton.md`, `docs/06-v1-scope-for-review.md` и прототип `prototype/lessons-1-2.html` (дизайн, экраны, логика уроков 1–2). Прототип одобрен помощницей как каркас v1.
- Не используем видео и фрагменты из сериалов. Не добавляем механики, которые пользователь не поймёт без объяснений (например, «заморозки» убраны).

## 1. Цель фазы 1

Закрытая веб-версия на `staging.vulilang.com`, доступная только администраторам. В ней работает каркас v1 из прототипа, но на настоящем движке:

1. Вход по почте (админы из списка разрешённых адресов).
2. 5 разделов нижнего меню: Учиться, Практика, Слова, Грамматика, Профиль.
3. Уроки 1–2 из прототипа, но данные уроков лежат в файлах контента, а не в коде интерфейса.
4. Прогресс, дни подряд, цель дня, XP, «Мои ошибки» хранятся на сервере и переживают смену устройства.
5. Повторение на алгоритме FSRS (слова из пройденных уроков).
6. Сброс прогресса (для проверки), выбор уровня.

Вне объёма фазы 1: подписка и оплата, публичный лендинг, говорение и ИИ-диалоги, мобильные приложения, импорт всех слов dizisub.

## 2. Предлагаемая архитектура: свой сервер (подтвердить с владельцем)

Решение владельца: свой хостинг, без Vercel и Supabase. Код и данные под полным контролем, без привязки к чужим платформам.

| Слой | Выбор | Зачем |
|---|---|---|
| Язык | TypeScript везде | Общий код для сайта и будущих приложений |
| Сайт | Next.js (App Router) + Tailwind CSS | Быстрый старт, подходит для лендинга и приложения |
| База данных | PostgreSQL на вашем сервере | Надёжная, бесплатная, хорошо масштабируется |
| Работа с БД | Drizzle ORM, миграции в репозитории | Структура БД версионируется и воспроизводится |
| Вход | Одноразовый код из 4 цифр на почту, без пароля. Библиотека Better Auth (плагин Email OTP) или Auth.js со своей проверкой кода; позже Google, Apple, passkeys | Пользователи в вашей БД; актуальность библиотеки проверить при старте |
| Письма | Resend (решение владельца); домен vulilang.com подтверждается записями SPF/DKIM в DNS | Код входа и уведомления; провайдер заменяем через общий интерфейс |
| Файлы (озвучка, картинки) | папка на сервере, позже S3-совместимое хранилище и CDN | Просто на старте, расширяемо |
| Запуск | Docker Compose: Caddy (HTTPS автоматически), сайт, PostgreSQL | Одинаково на любом сервере |
| Выкладка | GitHub Actions: сборка → отправка на сервер по SSH | Выкладка одной кнопкой/слиянием |
| Резервные копии | ежедневный дамп БД + зашифрованная копия вне сервера | Защита от потери данных |
| Мониторинг | Uptime Kuma, логи, письмо при падении | Узнаём о проблемах первыми |
| Безопасность | вход только по SSH-ключу, фаервол (ufw), fail2ban, автообновления, секреты только на сервере | Базовая защита |

Что это значит для владельца: сервер нужно содержать (обновления, копии, безопасность). Claude подготовит скрипты и пошаговые инструкции, но ответственность за доступы остаётся у вас.

**Где хранить данные.** Выбор страны сервера зависит от аудитории и закона о персональных данных (например, российский закон требует хранить базы персональных данных граждан РФ на серверах в РФ; в ЕС действует GDPR; в Турции KVKK). До выбора сервера определить: где живёт владелец и для кого сайт. Юридически подтвердить с юристом.

**Что нужно знать о хостинге до старта:** тип (VPS/VDS с root-доступом, а не обычный cPanel-хостинг для PHP), страна и провайдер, система (рекомендуется Ubuntu 24.04 LTS), минимум 2 ядра, 4 ГБ памяти, 40 ГБ диска. Для обычного cPanel-хостинга этот стек не подходит.

## 3. Формат контента

Уроки и слова хранятся как файлы (YAML/JSON) в `content/`, с идентификаторами, а не текстом внутри интерфейса. Это нужно для проверки правил курса и для будущей многоязычности.

Пример предложения (из `docs/03-course-skeleton.md`):

```yaml
sentence:
  tr: "Evim kırmızı."
  ru: "Мой дом красный."
  tokens:
    - { lemma: ev,      form: evim,    features: [poss_1sg], intro: lesson_05 }
    - { lemma: kırmızı, form: kırmızı, features: [],         intro: lesson_03 }
```

**Валидатор курса (обязателен):**
1. До 4–5 новых слов на урок и не более 1 новой грамматической идеи.
2. В одном предложении не более одного нового элемента.
3. Не менее 60% заданий на уже изученном.
4. Каждое слово встречается минимум 5 раз в ближайших уроках.
Валидатор запускается в CI и падает, если правила нарушены.

## 4. Данные (черновая схема)

- `profiles` (пользователь, уровень, цель дня, напоминание)
- `lessons_progress` (урок, статус, дата, точность)
- `srs_cards` (пользователь, слово, параметры FSRS, следующая дата)
- `weak_words` (пользователь, слово, вес ошибок)
- `practice_days` (пользователь, дата, число занятий), `xp_events`
- `admins` (разрешённые почты)

Контент курса остаётся в файлах; в БД храним только идентификаторы слов и уроков.
RLS (правила доступа): пользователь читает и пишет только свои строки.

## 5. Порядок работ (предлагаемые задачи)

1. Репозиторий, монорепозиторий, линтер, типы, тесты, CI на GitHub.
2. Каркас `apps/web` и перенос дизайн-токенов и компонентов из прототипа (тёмная/светлая темы, нижнее меню, карточки).
3. Настройка сервера и развёртывание на `staging.vulilang.com`, вход админов.
4. Движок уроков в `packages/core`: типы заданий из прототипа, валидатор, FSRS.
5. Уроки 1–2 как файлы контента, подключение к плееру урока.
6. Хранение прогресса, дней подряд, цели дня, XP, ошибок в БД.
7. Разделы «Практика», «Слова», «Грамматика», «Профиль» на данных.
8. Доступность, адаптивность, проверка на телефоне.

Критерий готовности фазы 1: админ заходит на `staging.vulilang.com`, проходит уроки 1–2, закрывает приложение, открывает на другом устройстве и видит тот же прогресс; повторение показывает пройденные слова.

## 6. Безопасность и порядок работы

- Секреты (пароль БД, ключи, SSH-ключ деплоя) хранятся только на сервере (`.env`) и в секретах GitHub Actions, а локальный `.env` в `.gitignore`. Не коммитить, не вставлять в чат.
- Двухфакторная защита на GitHub, на регистраторе и у хостинг-провайдера.
- Ветки: разработка в отдельной ветке, слияние через pull request после проверки; pull request создавать только по просьбе владельца.
- Перед публичным запуском: консультация юриста (товарный знак Vuli, политика конфиденциальности, условия, права на реплики), проверка примеров турецкого носителем.

## 7. Открытые вопросы к владельцу

1. Хостинг: тип, провайдер, страна, доступы (см. раздел 2). Секреты в чат не вставлять.
2. Согласие на выбранный стек.
3. Когда будет доступ к данным dizisub (импорт — фаза 2).
4. Список почт администраторов.

## 8. Вход по коду из 4 цифр
- Схема: пользователь вводит почту → получает одноразовый код → вводит → получает сессию на длительный срок (30–90 дней; в приложении токен в защищённом хранилище). Пароля нет.
- Защита (обязательна для 4 цифр): код живёт 10 минут и одноразовый; максимум 5 попыток на код; новый код отменяет старый; не более 5 запросов кода в час на почту и ограничение по IP; защита от ботов (Cloudflare Turnstile или аналог); одинаковый ответ на любую почту (не выдаём, есть ли такой пользователь).
- Для администраторов и закрытого стенда: список разрешённых почт и код из 6 цифр (или passkey).
- Дальше: Google, Apple (обязательно для iOS, если есть другие соцвходы), passkeys.

## 9. Git и защита кода
- Рабочий репозиторий: приватный GitHub (Claude-сессии в облаке работают с GitHub). Данные пользователей в Git не попадают: они только на сервере.
- Утечки случаются из-за: секретов в коде, отсутствия 2FA, случайно открытого репозитория, лишних приложений с доступом. Меры: 2FA, `.env` в `.gitignore`, секреты только в GitHub Actions и на сервере, сканирование секретов, защита основной ветки, доступ Claude только к нужным репозиториям, периодический аудит подключённых приложений.
- Резерв: ночное зеркало репозитория на своём сервере (Forgejo/Gitea), чтобы код не зависел от одной платформы.

## 10. Путь к мобильным приложениям
- Общий код в `packages/core` (движок уроков, валидатор, FSRS, типы и схемы API, дизайн-токены).
- Мобильное приложение: Expo (React Native) на TypeScript, использует `packages/core` и тот же API. Быстрый вариант проверки: обёртка веб-версии (Capacitor), но качество ниже.
- API с самого начала версионируем (`/api/v1`) и описываем схемами, чтобы мобильное приложение могло обращаться к нему же.
- Десктоп: веб-версия как PWA, позже оболочка (Tauri).
